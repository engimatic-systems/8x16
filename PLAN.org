* Work Plan

** Source Directive

This project uses a single literate Org source file =8x16.org= as the canonical implementation surface once code begins.

- Edit the =8x16.org= source, not tangled Odin output.
- Tangle generated Odin files into the repo and commit them.
- Mark generated files with "edit the org source".
- Wrap each tangled block with =BEGIN org:block <name>= and =END org:block <name>= comments.
- Keep block granularity at top-level Odin declarations or procedures.
- Use block markers to map compiler diagnostics in tangled files back to the org source.
- Do not build reverse-formatting or formatter-sync tooling unless Odin formatter support appears and the need becomes concrete.

** Merge directive

DO NOT merge PRs. The PR train is intended to support human operator review.
  
** PR 1: Spec And Skeleton

Goal: establish the repo, package boundary, and non-raylib data model.

Deliverables:

- =SPEC.org=
- package directory
- core public types: =Cell_Rect=, =Pixel_Rect=, =Color=, =UI_ID=
- no backend dependencies
- small README

Review question: does the package boundary express the intended 8x16 constraints without leaking =auto= concepts?

** PR 2: Geometry And Hit Testing

Goal: prove the core geometry.

Deliverables:

- =cell_rect=
- =rect_rel=
- =rect_px=
- =contains=
- validation/debug behavior for invalid rects
- unit tests or small example checks

Review question: are rects clearly absolute value geometry, not a layout tree?

** PR 3: Input State And Activation

Goal: implement release-inside control activation.

Deliverables:

- =UI_State=
- mouse button state ingestion
- press-origin tracking
- =hit_any= / =activated_any=
- button activation tests/examples

Review question: does interaction state stay minimal and caller-owned?

** PR 4: Drawing Command Layer

Goal: keep package independent of raylib while still useful to raylib callers.

This PR supersedes the earlier =pr4-drawing-command-layer= and =pr5-controls-and-examples= branches. Treat those branches as implementation reference only, not as base branches.

Deliverables:

- primitive draw command structs only: =Fill_Rect=, =Stroke_Rect=, =Text=
- =Pixel_Point= for text origin
- text command uses pixel origin, not =Pixel_Rect=
- no =Bar= draw command; bars compile to rectangle commands
- no semantic =Box=, =Button=, =Toggle=, or =Panel= draw commands
- caller-owned or UI-owned fixed command buffer
- =ui_end= returns ordered command slice
- integer text scale =1|2|3|4=
- loud command-buffer overflow behavior

Review question: does the draw layer expose only primitive rendering facts, with UI semantics resolved before commands reach a backend?

** PR 5: Command Compiler

Goal: turn UI semantics into primitive draw commands.

This PR should be rebuilt on top of the replacement PR 4.

Deliverables:

- =UI= frame object or equivalent call surface containing state, style, and command buffer
- =ui_text=
- =ui_box=
- =ui_panel=
- =ui_bar=
- =ui_button=
- =ui_toggle=
- style resolution to raw =Color= values
- text measurement using fixed 8x16 metrics
- text overflow warning before command emission
- bars compile to primitive rectangle commands
- buttons and toggles compile to primitive rectangle/text commands
- snapshot command-list tests for controls

Review question: is the compiler boundary clear: UI intent enters, primitive ordered draw commands leave?

** PR 6: Raylib Backend

Goal: prove that the command buffer is enough for a concrete renderer without adding raylib to core.

Deliverables:

- separate backend package, likely =raylib_8x16=
- font loading and backend font handle ownership
- texture filter setup
- renderer for =Fill_Rect=, =Stroke_Rect=, and =Text=
- support text scale =1|2|3|4=
- backend smoke example

Review question: can raylib render the command buffer without needing UI semantics, style resolution, clipping decisions, or input routing?

** PR 7: Example Workbenches

Goal: pressure-test taste and API ergonomics after the compiler and backend exist.

Deliverables:

- at least two small example surfaces
- dense control panel example
- bars, toggles, buttons, text, panels
- command snapshot tests where stable
- raylib visual smoke where useful

Review question: do the examples reveal a pleasant API without adding speculative layout helpers?
